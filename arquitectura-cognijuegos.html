02 / GENERAL

Arquitectura general del sistema

Cognijuegos presenta desafíos cognitivos diarios y una experiencia narrativa. El frontend reúne la interfaz del jugador y la administración. El backend entregado es una API modular con autenticación externa, MongoDB y módulos de juegos que quedaron fuera del arranque activo.

Persona → Interfaz React → HTTP / JSON → FastAPI → MongoDB

Seleccione un componente para consultar su responsabilidad y sus dependencias.

Estilo arquitectónico

El frontend es una SPA organizada por funcionalidades: navega entre pantallas sin descargar una página completa cada vez. El backend es un servicio FastAPI modular, con routers, esquemas y servicios por dominio. Comparte un proceso y una base de datos; sus carpetas no son microservicios independientes. El autenticador sí es una dependencia externa.

Dos repositorios distintos

juegos-mayores-actualizaciones contiene la experiencia Cognijuegos. mayores_actualizacionesSIPI-BACK publica hoy acceso de alumnos y progreso de cursos de Mayores Actualizaciones. Conserva código de juegos, pero esa presencia no garantiza compatibilidad.

Servicio externo de autenticación

El backend delega PIN y verificación de token en AUTH_SERVICE_URL. El servicio externo tiene su propio ciclo de vida y código, que no está en estos dos repositorios. No se puede reconstruir todo el ecosistema únicamente con estas carpetas.

05 / FRONTEND

Arquitectura del frontend

React 19 y TypeScript construyen la interfaz; Ionic aporta la estructura de app, React Router 7 decide la pantalla y Vite 8 sirve y compila el proyecto. El estilo combina Tailwind 4 y CSS específico.

index.html → main.tsx → Redux Provider → App.tsx → AppRoutes

Responsabilidades de arranque

  1. main.tsx crea la raíz de React e instala el store de Redux.
  2. App.tsx inicializa Ionic, monta PlayerEconomyProvider y las ventanas globales de tienda y pistas.
  3. routes.tsx contiene un único BrowserRouter, las rutas y los redireccionamientos de acceso.
  4. El menú ofrece cada juego; se entra primero al calendario y después a la partida.

LENGUAJE · IDENTIFICADOR: wordle

Palabra del día

Calendario → palabra de cinco letras → resultado por intentos.

Aa

Interacción del jugador

Escribe una palabra de cinco letras mediante el teclado táctil o físico. Cada letra se evalúa como correcta, presente en otra posición o ausente. El evaluador descuenta coincidencias para manejar letras repetidas.

Reglas implementadas

  • Gana al coincidir exactamente con la solución.
  • El tablero crece con los intentos: seis filas iniciales no significan un límite de seis oportunidades.
  • El envío verifica longitud y evalúa letras localmente; no hay consulta de diccionario en ese manejador.
  • Calificación por intentos: hasta 2 → S; de 3 a 4 → B; desde 5 → C.

Estado y persistencia

Conserva la solución activa, las palabras enviadas con sus evaluaciones, el texto todavía sin enviar y la pista comprada. Usa useClassicChallenge para cerrar el resultado y attemptsService para persistirlo.

Pistas e integración

La compra pide una pista textual a /api/economy/use-hint. No basta con mostrar un saldo: ese endpoint no existe en el backend entregado.

Archivos principales

  • WORDLE/WordleCalendar.tsx
  • WORDLE/WordleGame.tsx → evaluateGuess
  • JUEGOS/classicScoring.ts

LÓGICA · IDENTIFICADOR: sudoku

Sudoku diario

Tablero 9 × 9, bloques 3 × 3, notas y dificultad.

1–9

Interacción del jugador

Completa las celdas vacías sin repetir números en fila, columna o bloque. Puede seleccionar una celda, escribir, borrar, activar notas y pedir una pista para una posición.

Componentes y responsabilidades

  • SudokuGame compone la pantalla.
  • useSudokuGame coordina selección, notas, errores, restauración y victoria.
  • sudokuEngine genera tableros y comprueba conflictos.
  • SudokuBoard y SudokuKeypad renderizan los controles.

Configuración y guardado

El desafío puede aportar tablero y solución. El motor local usa la librería sudoku y guarda un tablero por fecha y nivel en caché. El nivel 1 revela 18 casillas extra; el 2, 10; el 3 usa el tablero base. La fecha es clave de caché, no semilla determinista de la generación.

La partida guarda celdas, solución, notas, dificultad, errores y tiempo. Los errores no agotan vidas en el flujo actual; el README que describe tres vidas está desactualizado.

Resultado

Se calcula con escalas de tiempo compartidas. Las pistas compradas se aplican con el valor confirmado por la API.

  • SUDOKU/useSudokuGame.ts
  • SUDOKU/sudokuEngine.ts
  • SUDOKU/sudokuStorage.ts

ATENCIÓN Y LENGUAJE · IDENTIFICADOR: sopa_letras

Sopa de letras

Buscar palabras temáticas en una grilla.

AB

Interacción del jugador

Selecciona un tramo de letras arrastrando o marcando un inicio y un final. Cuando el texto coincide con una palabra pendiente, se resaltan las celdas y se actualiza la lista.

Reglas que debe respetar el contenido

  • El validador acepta horizontal de izquierda a derecha y vertical de arriba hacia abajo.
  • No valida diagonales ni recorridos invertidos en esta revisión.
  • Termina al encontrar todas las palabras objetivo; la cantidad proviene de la configuración.
  • Una selección incorrecta de al menos tres letras suma un error, sin cortar la partida por vidas.

Datos y recuperación

Recibe grilla, palabras y tema desde el desafío. Si no llegaron por navegación, consulta el desafío por fecha. También hay valores predeterminados locales: distinguirlos del contenido remoto es esencial al depurar.

Guarda palabras encontradas en guesses, errores, pistas compradas y tiempo en gameData. La puntuación utiliza el tiempo empleado.

Pistas

Solicita por índice una pista de una palabra aún pendiente. El servidor debe confirmar la compra y el saldo.

  • SOPA_LETRAS/SopaLetrasCalendar.tsx
  • SOPA_LETRAS/SopaLetrasGame.tsx → checkSelection

VOCABULARIO Y ASOCIACIÓN · IDENTIFICADOR: crucigrama

Crucigrama

Pistas numeradas, palabras horizontales y verticales.

▦

Interacción del jugador

Selecciona una pista o celda, completa letras y resuelve las palabras cruzadas. La pantalla coordina foco, dirección de escritura, teclado y validación del tablero.

Modelo del tablero

WordDef define número, dirección, palabra, longitud, coordenadas y pista. CellDef indica fila, columna, letra, numeración y si la celda está bloqueada.

La separación entre palabras y celdas permite que dos palabras compartan una letra en un cruce.

Usa almacenamiento específico del juego junto con el servicio común de partidas. La finalización pasa por useClassicChallenge, con puntuación por tiempo. Los errores no consumen un cupo de vidas del clásico.

08 / DISEÑO

Patrones de diseño: reglas y presentación

Diseño inicial del 5/11: patrones, gráfico animado y laboratorio de garantías futuras

Se conserva el material original. Los endpoints v3, commandId y versiones del run son propuestas de este diseño inicial; no están publicados en el contrato V2 leído el 6/11. Para integrar el front actual, usar la actualización de arriba.

Propuesta para evolucionar King’s Court: motor de acciones autoritativo en backend y máquina de estados de presentación en frontend. Una intención produce una transición confirmada; la interfaz explica sus consecuencias.

Criterio para implementarCambios necesarios > código y funcionamiento actual > GDD. El GDD aporta contexto; sus cantidades y reglas históricas no reemplazan el comportamiento vigente. Este capítulo describe una propuesta del 5 de noviembre de 2026, no una integración ya desplegada.

Abrir especificación .md para otro agente ↗

Qué problema resuelve

Hoy hay efectos calculados en el slice local y otros en el motor remoto. Eso permite porcentajes distintos, recompensas duplicadas y avances que dependen de qué pantalla se abrió. La propuesta concentra la verdad de la partida en el servidor y hace explícito qué puede solicitar el cliente.

Intención → Validar fase y versión → Ejecutar ECA → Guardar y emitir recibo → Reemplazar snapshot → Animar

Nombre de cada patrón y por qué se usa

La propuesta combina patrones de comportamiento y de arquitectura. El motor de acciones es el conjunto resultante; no es el nombre de un único patrón.

Nombre y tipoDefiniciónAplicación en King’s Court
Command · patrón de comportamientoRepresenta una solicitud como un objeto y separa a quien la solicita de quien la ejecuta. Aquí usamos un mensaje serializable y un command handler en el servidor.La UI crea AVANZAR_MES; narrativeService lo transporta; el handler coordina el dominio. commandId identifica la intención, pero la idempotencia requiere además guardar y validar recibos.
Finite State Machine (FSM) · modelo de comportamientoDefine estados finitos y transiciones por evento. Cada transición puede tener un guard y acciones. Solo se aceptan los eventos habilitados en el estado actual.Dos FSM distintas: la de dominio autoriza el avance de la partida; la de presentación espera HTTP, muestra consecuencias y habilita la vista confirmada.

¿FSM y el patrón State de GoF son lo mismo?

FSM es el modelo de estados y transiciones. State, del catálogo GoF, delega el comportamiento de un objeto a objetos que representan sus estados. Es una forma posible de implementar comportamiento dependiente del estado, pero no obliga a usar tablas ni reemplaza el diseño de la FSM.

Esta propuesta usa tablas de transición y funciones: no necesita una clase por fase ni afirma haber implementado State de GoF. Una librería como XState puede ejecutar el modelo del front si aporta valor; no es un requisito del contrato.

Técnicas complementarias, con sus nombres

ECA (Event–Condition–Action) es el modelo de reglas declarativas: un disparador selecciona efectos, una condición decide si aplican y una acción modifica el dominio. Backend autoritativo es la decisión de que el servidor sea dueño de la verdad persistida. Idempotencia evita repetir efectos del mismo comando y Optimistic Concurrency Control rechaza intenciones basadas en versiones viejas. Son mecanismos distintos; una FSM sola no resuelve los cuatro.

Lecturas: Command y command handler · MicrosoftEstados y transiciones · StatelyPuertos y adaptadores · AWS

Cómo se lee una transición

origen + evento [guard] / acciones → destino. El estado indica qué eventos pueden aceptarse; el evento informa qué ocurrió; el guard es una comprobación sin efectos; las acciones son el trabajo autorizado por esa transición; el contexto guarda datos como mes, oro, versión o comando pendiente.

Ejemplo front: listo + INTENCION [sin pendiente] / enviar HTTP → enviando. Ejemplo back: BALANCE_MES + AVANZAR_MES [versión válida] / ejecutar reglas y persistir → DRAFT_MENSUAL. El evento local INTENCION y el comando remoto AVANZAR_MES tienen propósitos diferentes.

Turno, fase y pantalla son conceptos diferentes

El mes 3 puede contener draft, evento, conversación y balance. Recibir «mes 3» no autoriza al front a generar otro mes. La fase confirmada decide la vista; el estado local decide si espera una petición o muestra una animación. Un GET reconstruye la pantalla sin activar cartas.

Gráfico animado: del clic al estado confirmado

Reproducí el recorrido para ver el comando viajar al backend y la respuesta volver al front. Podés pausar o elegir un paso. La máquina del front cambia al recibir mensajes; la del back confirma la fase y los recursos.

Probalo paso a paso: dos máquinas coordinadas por mensajes

El laboratorio ejecuta una operación por ejemplo. Resalta los estados activos y muestra origen, evento, guard, acción y destino de cada transición. Los botones «procesar» y «entregar» permiten pausar la red didácticamente; en la app real el servidor procesa y el servicio HTTP entrega el resultado automáticamente.

Por qué la fase confirmada no dispara otro POST

El servicio de transporte comunica el resultado a la FSM del front. Su transición actualiza los datos y prepara la vista. Al terminar la animación se muestra DRAFT_MENSUAL; obtener esa fase no llama automáticamente a AVANZAR_MES. La siguiente intención del jugador será ELEGIR_CARTA_MENSUAL.

Reglas para llevarlo al código real

Una carta que incrementa un atributo cada turno

La carta declara el disparador y sus acciones en datos del backend. Al avanzar de mes, el caso de uso valida el comando, reúne las cartas activas y ejecuta sus reglas. Guarda el nuevo saldo junto con el recibo y devuelve el snapshot más las consecuencias. El front muestra esa respuesta; no itera las cartas para repetir el incremento.

En King’s Court se ejemplifica con oro. «+10 vida» es un caso genérico: vida no es uno de sus cuatro recursos actuales. La política mensual revisada aplica cada_mes al entrar al siguiente mes no final; verificar que siga vigente antes de migrarla.

Resultado, conversación y reanudación

Una decisión puede llevar a RESULTADO_EVENTO aunque no altere recursos. La conversación puede afectar afinidad, recursos o nada. Resultado y opción elegida deben quedar identificados para recargar sin sortear otro desenlace. Si cerrar un resultado cambia el flujo persistido, usar un comando explícito de confirmación que no recalcule sus efectos.

Reintentos, dos pestañas y respuestas fuera de orden

El cliente conserva commandId, payload y expectedVersion mientras el resultado sea incierto. El servidor busca primero el recibo; la misma clave con otro payload se rechaza. Para una intención nueva, compara la versión antes de guardar. Estado y recibo deben confirmarse juntos: deshabilitar el botón solo mejora la UX.

Un conflicto obliga a recuperar el estado y revisar la nueva intención. Una respuesta vieja no reemplaza un snapshot más nuevo. Los IDs de consecuencias permiten evitar que la animación se repita; el azar del resultado se conserva en el recibo.

Migración pequeña y verificable

Identificar primero el backend que realmente atiende la web: el corte de backend analizado tiene servicios narrativos sin registrar. Comenzar por AVANZAR_MES con contrato tipado y pruebas; retirar el incremento local equivalente solo cuando su reemplazo esté operativo. Seguir con adquisición, decisiones y conversación, conservando grafos, modo adaptado y cantidades vigentes.

No se necesita una reescritura ni event sourcing completo: estado, recibos y consecuencias alcanzan para empezar. La especificación Markdown detalla el orden de evaluación, DTOs, atomicidad, fallos, archivos afectados y criterios de aceptación.

Gestión de estado y persistencia en frontend

No hay un único almacén. La UI combina estado del componente, Redux, Context, almacenamiento del navegador y respuestas remotas. La responsabilidad de cada uno importa al depurar un saldo o una partida que reaparece.

El servicio común de partidas

attemptsService.ts aísla claves por usuario, juego y fecha. Un ejemplo de forma es game_active_progress_user_42_sudoku_2026-11-04; los invitados usan guest. Los días completados también separan año y mes.

Primero intenta leer localmente; si no hay progreso local y hay una cuenta, consulta el servidor. En las escrituras usa una cola en memoria por clave para evitar enviar cambios fuera de orden. El resultado final puede quedar con synced: false, y el hook ofrece reintentar la confirmación.

Guardado local no significa sincronización universalEl invitado no envía sus intentos al backend, pero el calendario y la configuración pueden hacer consultas de red. Tampoco hay aquí una cola durable de todas las acciones offline ni una resolución general de conflictos entre dispositivos.

Economía, pistas y actualización visual

El contexto consulta configuración y saldo, compra vidas, desbloquea días y abre el modal de pistas. pistasService requiere token y valida una respuesta con saldo restante. Un evento user_progress_updated comunica cambios a otras partes de la UI; por eso un saldo puede depender de Redux, sesión local y eventos.

Las vidas siguen existiendo en la economía y en el hook de Puzzles, pero los cuatro clásicos actuales no finalizan por agotarlas. No agregues ese comportamiento basándote únicamente en textos históricos.

11 / BACKEND

Arquitectura del backend

Alcance histórico de este capítuloLa base de este bloque corresponde al código fijado el 4/11. El contrato consultado el 6/11 sí publica narrativa, avance por grafos y catálogo de acciones. Para esos cambios, ver la revisión actual del coordinador; no interpretar «ausente» o «sin registrar» de la tabla histórica como estado del servidor actual.

FastAPI recibe HTTP, Pydantic describe y valida los datos, los servicios ejecutan operaciones y Motor consulta MongoDB. La separación es por dominio, con acceso a base de datos directamente desde los servicios.

Router → Schema Pydantic → Service → Motor / MongoDB

Arranque real

app/main.py crea la aplicación y su ciclo de vida. Al iniciar conecta MongoDB, realiza un ping, crea índices y siembra estados de usuario. Al cerrar libera la conexión.

Registra CORS, manejo uniforme de errores y los routers de auth y progreso. Desactiva /docs, /redoc y /openapi.json en esta configuración, sin condicionar esa decisión al entorno.

Qué significa async acá

Las consultas a MongoDB y al autenticador usan APIs asíncronas para esperar I/O sin bloquear ese flujo. Eso no convierte operaciones múltiples en una transacción ni garantiza atomicidad entre colecciones.

Ejemplo: una carta cambia los recursos

El servicio de turno busca la partida, comprueba su fase y que la carta fue ofrecida, carga su definición y despacha efectos al_obtener. El motor evalúa condiciones como poseer una etiqueta o superar un umbral de recurso. Si una acción provoca colapso, el servicio de finales cierra la partida; de lo contrario el director selecciona el próximo evento.

Las reglas están modeladas como datos: condición + disparador + acción. Esto permite variar contenido desde catálogos sin codificar una pantalla para cada historia. No debe confundirse este motor de efectos con el editor de grafos que agregó el frontend.

Modelo de datos e identidad

El autenticador es la referencia para la identidad numérica. El backend mantiene en MongoDB un perfil local con sus propios datos de progreso. Las colecciones de juegos guardan contenido y ejecuciones por separado.

estados_usuarioEstados como activo o suspendido.Índices únicos por id y codigo.

Dos estrategias de persistencia

Los cursos almacenan el progreso dentro del documento de usuario. Las partidas clásicas y narrativas tienen documentos propios. El segundo enfoque evita cargar todos los intentos al leer un perfil y permite consultar por fecha.

MongoDB no aporta claves foráneas como una base relacional: borrar un catálogo puede afectar referencias existentes. Revisá las validaciones del servicio y las partidas ya creadas.

Desafío no equivale a intento

Un desafío puede variar por dificultad, pero el índice del intento no la incluye. Si se quieren conservar varios resultados por nivel el mismo día, hay que acordar un cambio de identidad de partida tanto en el almacenamiento local como en API e índices.

La colección game_levels aparece en documentación de diseño del frontend; no se presenta aquí como una campaña operativa confirmada.

El recorrido de autenticación

  1. El cliente envía PIN o token al backend.
  2. auth/service.py consulta AUTH_SERVICE_URL/auth/validar-acceso para el servicio mayoresactualizaciones.
  3. Si está autorizado, sincroniza el usuario por ID mediante upsert y devuelve el formato esperado por el cliente.
  4. Las rutas protegidas de progreso usan get_current_user y comprueban que el usuario opere sobre su propio ID o sea administrador.
Limitaciones de autenticación que debe conocer quien mantenga el sistema

La decodificación local de JWT usa verify_exp=False; por lo tanto no verifica expiración, aunque otros comentarios sugieran lo contrario. También existe una validación remota alternativa cuando falla la decodificación local.

Los routers de juegos no registrados no tienen una política uniforme: intentos acepta IDs del request en algunos caminos; narrativa puede caer al usuario invitado 0; el router de administración narrativa no declara una dependencia administrativa global. No deben exponerse tal cual suponiendo que heredan las protecciones de progreso.

El limitador de acceso por PIN vive en memoria del proceso. No es un contador compartido entre réplicas. Estas observaciones provienen del código y no constituyen una prueba de la configuración efectiva de producción.

Ejemplo concreto: confirmar una victoria

Lo que hace el frontend

saveFinalGameAttempt envía identidad, juego, fecha, estado, intentos, calificación, estrellas, tiempo y datos de juego. En ese envío final no manda score; espera que el servidor devuelva el puntaje confirmado y, si corresponde, los puntos ganados y totales.

Lo que implementa este backend

El schema de entrada tiene score=100 por defecto y no declara calificación ni tiempo. El servicio suma req.score al usuario en una primera finalización y devuelve el intento, sin los campos nuevos de economía.

Compatibilidad de ruta ≠ compatibilidad de resultadoAunque se conectara el router, el cliente y el servicio no estarían acordando cómo calcular la recompensa. Además, el chequeo previo de finalización y el incremento de puntos son operaciones separadas; no hay una transacción que haga todo el cierre atómico.

14 / INFRAESTRUCTURA

Infraestructura y despliegue

Desarrollo

Vite sirve el frontend en 5174. El proxy envía familias como /api al destino definido por VITE_BACKEND_URL o VITE_API_URL; si no hay configuración usa http://localhost:8080.

Este backend usa 8082. Para probarlo a través del proxy hay que configurar ese destino. El proxy evita un problema de origen en el navegador; no inventa endpoints faltantes.

Despliegue del backend

Docker Compose levanta Caddy y FastAPI. Caddy expone 8082, sirve dist como SPA y reenvía las rutas de API al contenedor backend.

MongoDB no se crea en ese Compose: se alcanza mediante una red externa llamada red-mongo-compartida. La imagen del backend usa Python 3.12 y un usuario sin privilegios.

Automatización de despliegue

Ambos repositorios tienen GitHub Actions sobre main en runners propios. El frontend compila dentro de Node 22 y copia dist a un volumen de otro checkout. El backend inyecta configuración desde un secret y ejecuta docker compose up -d --build. Los workflows inspeccionados no ejecutan la suite de tests como requisito previo al despliegue.

Empaquetado Android

Capacitor envuelve la misma aplicación web en un proyecto Android. webDir apunta a dist, pero capacitor.config.ts tiene además una URL HTTP de una IP local en el puerto 5173. En esa configuración carga ese servidor; no hay que asumir que un APK resultante será autónomo o estará preparado para producción.

Requisitos de empaquetadoConfirmar la URL de API accesible desde el dispositivo, decidir si se usarán recursos empaquetados o un servidor remoto y alinear los puertos. El script de túnel también referencia 5173, mientras el Vite actual usa 5174.

17 / REPASO

Glosario técnico y verificación

SPA
Aplicación web que cambia de vista en el cliente. El servidor debe poder devolver index.html al abrir una ruta interna.
Router
En React decide la pantalla. En FastAPI conecta una URL y método con una función del servidor.
Hook
Función de React que encapsula estado y comportamiento reutilizable, como el ciclo de un desafío.
Slice de Redux
Parte del estado global con sus acciones y reductores. Un reducer transforma ese estado.
Context
Mecanismo para ofrecer datos u operaciones a componentes descendientes sin pasarlos por todas las props.
Schema / DTO
Forma declarada de un mensaje o documento. Pydantic lo usa para validar y serializar datos.
Upsert
Actualizar un documento si existe o crearlo si no existe, usando una condición de búsqueda.
Idempotencia
Repetir una operación no debe producir efectos adicionales no deseados, como cobrar o premiar dos veces.
JWT y Bearer
Token firmado y forma habitual de enviarlo en Authorization. La firma no reemplaza la autorización de cada recurso.
SSO
Acceso entre sistemas usando una identidad compartida. El panel espera intercambiar tickets de acceso.
Proxy inverso
Recibe la petición del navegador y la dirige al servicio adecuado; Caddy cumple esa función en despliegue.
Fallback
Comportamiento alternativo ante un fallo. El respaldo narrativo local no es la misma partida confirmada por el servidor.
Grafo narrativo
Conjunto de nodos y transiciones. Una opción lleva a otro nodo; el frontend tiene editor y consumidor de ese modelo.
CacheStorage y localStorage
La primera se usa aquí para imágenes; el segundo para datos pequeños de sesión, preferencias y progreso.
Verificación de conceptos

La carpeta de un módulo existe y su router define endpoints. ¿Eso asegura que la API los publica?

Conceptos a verificar

  • Qué datos son del desafío y cuáles de una partida.
  • Dónde guarda el frontend a un invitado y cómo confirma una cuenta.
  • Por qué el backend tiene código narrativo pero no expone sus rutas.
  • Qué hace cada clásico y por qué King's Court tiene otro flujo.
  • Qué depende del autenticador, de MongoDB y de una API de juegos compatible.
